# Auditoría de arquitectura, datos y preparación para producción

Fecha: 22 de octubre de 2026, America/Buenos_Aires. Diagnóstico del código presente en el espacio de trabajo; la integración de autenticación del frontend se está incorporando en esta misma tarea y se revisó su versión nueva, no la versión anterior sin cookies/CSRF.

## Alcance y límites

Se inspeccionaron modelos, tres revisiones de Alembic, rutas, repositorio, integración TMDB, configuración pública, Compose, dependencias y frontend. Se consultaron documentación y avisos oficiales y se ejecutaron inventarios de paquetes y `npm audit --json --ignore-scripts`. No se abrió `.env`, no se imprimieron credenciales, no se conectó esta auditoría a PostgreSQL, no se ejecutaron migraciones, instalaciones, reparaciones ni operaciones HTTP contra datos reales. El único archivo creado por esta auditoría es este informe.

Las referencias `archivo:línea` corresponden al código observado; pueden desplazarse con cambios posteriores. **Confirmado estático** significa que el comportamiento está presente en el código, no que se haya reproducido contra producción. **Potencial** requiere una condición de despliegue, concurrencia, volumen o datos que no se midió. **Mejora opcional** describe evolución o mantenibilidad, no una vulnerabilidad demostrada. Severidad: P1 alta, P2 media, P3 baja. No se afirma ningún P0 ni un incidente real.

No se verificaron el esquema instalado, `alembic_version`, índices efectivos, planes `EXPLAIN`, volumen de datos, configuración real del proxy, imágenes en ejecución, backups externos, dependencias del proceso desplegado ni capacidad con carga. Los inventarios Python son del intérprete disponible en esta máquina y no acreditan el entorno de producción.

## Estado de la arquitectura

La separación React → FastAPI → PostgreSQL/TMDB resulta adecuada para esta etapa. El token TMDB permanece en el backend. La colección ya tiene propietario obligatorio y unicidad por `(usuario_id, id_tmdb)`, y sus lecturas/escrituras filtran por usuario autenticado. Las notas personales siguen separadas de la valoración externa. Las consultas ORM observadas usan expresiones parametrizadas; no se encontró construcción de SQL mediante texto ingresado por el usuario.

El frontend nuevo tiene `AuthProvider`, `RequireAuth`, cliente HTTP con `credentials: "include"`, errores con estado HTTP, CSRF en memoria y revisión de sesión para descartar respuestas pertenecientes a otra sesión. Esto corrige la brecha que tenía la versión previa al backend autenticado. La cookie queda bajo control del navegador. Evidencia: `frontend/src/auth/AuthContext.jsx:8`, `frontend/src/auth/RequireAuth.jsx:5`, `frontend/src/services/apiClient.js:16`, `frontend/src/services/apiClient.js:65` y `frontend/src/App.jsx:26`.

La preparación para publicar sigue condicionada a reproducibilidad de instalación, revisión de migraciones, pruebas reales de aislamiento entre usuarios y un despliegue operable. No hace falta pasar a microservicios ni añadir una base no relacional para abordar estos puntos.

Para el despliegue nuevo se debe configurar `VITE_API_URL` (`frontend/src/services/apiClient.js:1`), URL pública, mismo sitio/hostname según la política de cookies y fallback de las rutas `/coleccion/:id`, `/pelicula/:id`, `/login` y `/registro`. La configuración de Vite no reemplaza configuración de hosting. Mantener públicos Descubrir/detalle de catálogo y proteger funciones personales también en servidor; un `RequireAuth` no es autorización de datos.

Límite operativo del harness: cambia la URL a una ruta de producto con `history.replaceState`. Editar `qa/main.jsx` durante una prueba puede hacer que Vite recargue completamente esa ruta y abra la entrada normal, sin interceptación de fixtures. Durante QA se debe mantener estable ese módulo y reiniciar siempre desde `/qa/index.html?...` o el control de recarga del panel. Una vista normal tras HMR no demuestra un fallo de logout ni una pérdida de sesión del fixture. No realizar acciones de escritura si el panel de datos simulados desapareció.

## Evolución hacia perfiles, amigos, reseñas y anime

Estas propuestas son **mejoras opcionales (P3)**, salvo controles de autorización/privacidad que se vuelven requisito al habilitar contenido compartido. No son funcionalidades existentes ni cambios implementados.

| Área | Diseño incremental propuesto | Decisión previa necesaria |
| --- | --- | --- |
| Perfil público | Separar respuesta pública de `UsuarioRespuesta`, que hoy contiene email (`app/schemas/usuarios.py:20`). Incorporar nombre visible, alias estable, biografía y avatar validado; exponer únicamente campos públicos. | Qué datos se comparten por defecto y qué identificador se puede cambiar sin romper enlaces. No reutilizar `/usuarios/me` para perfiles ajenos. |
| Visibilidad | Política explícita de colección, actividad y reseña: privada, amigos, pública. Comprobar autorización en cada consulta de backend y en sus contadores; índice/cache debe respetarla. | Privado por defecto, comportamiento al bloquear, revocar amistad o cambiar visibilidad y necesidad de ocultar existencia con 404. |

| Catálogo compartido | Mantener por ahora snapshots de título/año/póster por colección (`app/db/models.py:38`). Al agregar contenido social, revisar también exportación/borrado de cuenta, minimización de datos, moderación y políticas de retención con asesoramiento adecuado al alcance real. Este informe no valida obligaciones legales.

## Orden de trabajo recomendado

1. **Reproducibilidad y preservación de datos:** resolver ARQ-01/04, revisar upgrade/downgrade y configuración no versionada, preparar backup y probar un clon/base descartables. No ejecutar la migración destructiva contra datos valiosos como comprobación.
2. **Validación del flujo autenticado ya integrado:** ejecutar las pruebas de cliente y harness nuevos, y comprobar dos usuarios, sesión vencida, 403 CSRF, desconexión, cambio de cuenta y permisos con DB descartable. Resolver la superficie legacy antes de exponer la API.
3. **Fiabilidad de escritura y proveedor:** carrera de alta, traducción de errores DB/TMDB, sacar SQL síncrono del event loop y reutilizar cliente externo. Tests concurrentes en DB aislada, sin prometer que el lock del navegador los reemplaza.
4. **Publicación controlada:** dependencias reproducibles, CI, URLs/orígenes, HTTPS, build estático, healthchecks, migraciones como paso explícito, logs redaccionados y restore ensayado.
5. **Escalar según medición:** paginar/medir e indexar; después privacidad/perfiles/amigos/reseñas; ampliar movie/tv/anime con modelo de identidad explícito.

No se modificaron modelos, rutas, migraciones, Docker, requirements, configuración ni archivos fuente del frontend para elaborar este diagnóstico. Las correcciones descritas son propuestas para tareas posteriores; este documento no las declara realizadas.
